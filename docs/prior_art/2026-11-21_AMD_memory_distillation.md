## 2. Математика статьи (вся, что в ней есть)

Формализм короткий: одна целевая функция и определения записей памяти. Обучения, функций потерь и теорем нет.

**Постановка (§3.1).** Агент π вызывает инструменты из множества 𝓕. Траектория τ = ((a₁,o₁),…,(a_T,o_T)), a_t ∈ 𝓕 — вызов, o_t — наблюдение. Учитель π^T проходит набор задач 𝓢 и даёт 𝓓^T = {τ^T₁,…,τ^T_N}, N = |𝓢|. Из них строится память 𝓜, ученик π^S решает **тот же** набор 𝓢 с памятью. Цель:

    max_𝓜  E_{s∼𝓢} [ R( π^S(s; 𝓜) ) ]        (1)

R — награда «задача решена». Максимизация по 𝓜 не выполняется никаким алгоритмом: 𝓜 строится по фиксированному рецепту, формула (1) — только запись цели.

**Память (§3.2).** Строится только из успешных траекторий 𝓓^T₊ ⊆ 𝓓^T; 𝓜 = 𝓜^wf ∪ 𝓜^st ∪ 𝓜^fn.

| Уровень | Запись | Содержимое | Индекс |
|---|---|---|---|
| Workflow | m^wf_i = (q_i, ins_i) | запрос-описание задачи и словесная стратегия; значения заменены метками `<ID>`, `<EMAIL>` | вектор |
| Subtask | m^st_{i,k} = (ℓ_{i,k}, d_{i,k}, e_{i,k}) | метка, описание в одно предложение, отрезок траектории: исполнимый код и наблюдения; не более 6 отрезков на траекторию | вектор описания d |
| Function | m^fn_{i,j} = (f_{i,j}, E_{i,j}, doc(f_{i,j})) | имя функции, пример вызова с контекстом, документация (если есть) | имя функции |

Разбиение на отрезки делает LLM учителя с подсказками по границам вызовов API.

**Выборка и подстановка (§3.3, прил. A, C).**
- Вложения — `text-embedding-3-small`, близость — косинус, кандидаты ниже порога δ отбрасываются. Значение δ в статье не названо.
- До начала задачи: top-1 Workflow по тексту задачи; ученик сам делит задачу на метки подзадач (до 6), по каждой берётся top-1 Subtask с удалением повторов. Всё идёт в системный промпт.
- По ошибке вызова: по имени упавшей функции берутся записи Function, ранжируются косинусом к задаче, top-1 дописывается к сообщению об ошибке.
- k = 1 для всех уровней; предел — 40 шагов на задачу.

## 4. Наши правила, применённые к их данным

Пересчёт мой, по опубликованным долям. Данных по задачам нет, поэтому интервалы — для двух независимых долей (нормальное приближение). Сравнения на самом деле парные (одни и те же задачи), парный интервал может быть уже; посчитать его по статье нельзя. Скрипт пересчёта не сохранён: формула — d ± 1,96·√(p₁(1−p₁)/n + p₂(1−p₂)/n).

**4.1. Утечка: в основной таблице память построена на тех же задачах, на которых меряют ученика.** Это прямо записано в §3.1 и признано в прил. B.3. При k = 1 и запросе «текст задачи» ближайшая запись Workflow — с большой вероятностью запись самой этой задачи, если учитель её решил. Проверка без утечки сделана только для одного ученика из четырёх.

|---|---|---|---|
| Основная таблица (своя задача в памяти) | +34,5 [+25,2; +43,8] | +23,0 [+14,6; +31,4] | +3,9 [−5,5; +13,3] |
| Своя задача исключена | +31,6 [+22,3; +40,8] | +15,5 [+7,4; +23,6] | +7,0 [−2,7; +16,7] |
| Разбиение 7:3 (≈ 50 / 60 / 39 задач) | +25,0 [+8,0; +42,0] | +14,5 [−0,4; +29,4] | +6,3 [−11,4; +23,9] |

Вывод: эффект на AppWorld и BFCL сохраняется без утечки. На BFCL заголовочная величина завышена примерно на треть (23,0 → 15,5); сама разность 7,5 п. п. имеет интервал [−1,8; +16,8]. Для трёх остальных учеников и для чужих методов сравнения проверки без утечки нет.

**4.2. ToolSandbox: прирост не отличим от нуля ни у одного ученика** при непарном интервале: +3,9; +3,5; +5,4; +0,8 п. п. при стандартной ошибке 2,9–5,2 п. п. Прирост Llama +0,77 — это одна задача из 129. Разброс ±0,8 п. п. из табл. 5 — шум повторного прогона модели на тех же задачах, а не выборки задач.

**4.3. «Ученик превосходит учителя» данными не подкреплено.**
- AppWorld: Gemma 54,17 против 50,00 — разность +4,2 [−6,5; +14,8]; Qwen3-8B +1,8 [−8,9; +12,5].
- BFCL: Gemma4-E4B и Qwen3-8B **без памяти** уже равны учителю (37,25 и 38,00 против 36,50). Превышение там — не следствие дистилляции. Разность Gemma с AMD — +9,5 [−0,1; +19,1].
- Объяснение авторов («ученик переосмысляет образцы под своими индуктивными смещениями») не проверялось.

**4.4. Правда берётся от кода, и она же отбирает память.** Успех в AppWorld — юнит-тесты состояния базы, в BFCL — сверка состояния API, в ToolSandbox — вехи, написанные людьми. Как именно отбирается 𝓓^T₊, в статье не сказано; по умолчанию — тем же оценщиком бенчмарка. Значит, память отфильтрована правдой тестового набора. В применении правды нет: успех траектории учителя должен определять судья. Что будет с памятью, когда фильтр ошибается, статья не меряет. Это и есть главный вопрос Neu.

**4.5. Множественные сравнения и мощность.** Предрегистрации нет, мощность не считалась, поправок нет. Таблица 3 (четыре учителя) — четыре точки; вывод о «совместимости учителя и ученика» — описательный.

**4.6. Описательное наблюдение по табл. 3 (моё, не проверялось).** Отношение точности ученика к точности учителя: у Qwen3-4B — 0,52; 0,47; 0,99; 0,86; у Qwen3-8B — 0,65; 0,70; 1,04; 1,14. Точность ученика упирается примерно в 50–59 % независимо от того, что учитель решил 84 или 153 задачи из 168; ряд по размеру ученика тоже выходит на 52–53 %. Похоже на потолок самого ученика, а не памяти. Причина не проверялась.

## 5. Их результаты, применённые к Neu

**5.1. Это тот же класс системы, что и Neu.** Слова автора 27.09.2026: «набор препромптов для сильного „мотора“». AMD — измеренный пример: слой текста поверх чужого мотора переносит умение от дорогой модели к дешёвой без дообучения. Для экономики токенов (`docs/2026-11-09_token_economy.md`, Т1: Haiku вместо Opus) это опора: дорогая модель решает один раз, дешёвая исполняет много раз.

**5.2. Соответствие уровней.**

| AMD | В Neu сейчас | Что говорит AMD |
|---|---|---|
| Workflow — словесная стратегия до начала | `CLAUDE.md`, `PROTOCOL.md`, роли совета | один этот слой даёт мало: +7 п. п. из +34,5 на AppWorld |
| Subtask — исполнимый образец отрезка | `tools/`, `run_queue.sh`, навык `research-journal` — частично | главный вклад: +25 п. п.; тот же слой текстом — 23,21 против 49,40 |
| Function — подсказка по имени в момент ошибки | `journal/ERRORS.md` и хук начала сессии — но показываются заранее и текстом | подсказка по сбою не раздувает контекст; вклад малый |

**5.3. Следствия для наших голов (гипотезы, не проверены на Claude).**
1. Дешёвым головам правила давать исполнимым образцом, а не прозой. У нас почти весь перенос — проза.
2. Меньше и точнее: одна ближайшая запись лучше пяти. Хук начала сессии выдаёт сводку всем подряд; по AMD лишние записи вредят малой модели.
3. Уроки из ERRORS подавать в момент сбоя и по ключу (имя инструмента, файла), а не списком в начале.
4. Перенос проверен на моделях 4–8B и на вызовах инструментов. На Haiku 5.5 и на наших задачах (законы, игры, тестировщик) не проверен; статья сама ограничивает вывод текстовыми бенчмарками с фиксированным набором функций.

**5.4. Чего у AMD нет, а у Neu есть.** Оценщик без правды, раздельный учёт незнания и самообмана (ИОИ), предрегистрация, контроль утечки. AMD не меряет, становится ли ученик с чужой памятью увереннее там, где ошибается.

## 6. Предложения (в опись; новые линии заморожены решением автора 12.10.2026)

| ID | Что | Мера | Правда |
|---|---|---|---|
| AMD-1 | Память Opus → Haiku на задачах Neu с правдой от кода. Руки: без памяти; Workflow; Workflow + Subtask; память только из других задач | точность; незнание и самообман отдельно (ИОИ); цена в токенах | код |
