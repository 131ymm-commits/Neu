## 4. Анализ (`analyze_precond02.py`)
- **Регрет голоса** — как PRECOND-01 §4. Нормированный регрет; отказ (−1) → регрет выбора по заявке A0; сбой, пропуск, недопустимый номер → 1; задача исключается, если лучший − средний ≤ EPS (150). После правды повторов нет.
- **Мера руки на задаче** — средний регрет пяти голосов. Выигрыш задачи g = NOREF − ANCHOR (g > 0 ⇔ REFUSE помогает); действие REFUSE = −g.
- **Первичный тест (один, α = 0,05, односторонний).** t по задачам, H1: среднее g > 0.
  - План — групповой последовательный с одним промежуточным анализом после этапа A (`plan.json`: n1 = 180, n_max = 360).
  - Граница эффективности — расход α по Lan–DeMets типа O'Brien–Fleming. При t1 = 1/2: c1 = 2,538 (номинальное p 0,0056) и c2 = 1,662 (p 0,0482). Проверка — эталон 2,963 и 1,969 при α 0,025 (`dryrun_precond02.py`).
  - Номинальное одностороннее p t-теста сравнивается с 1 − Φ(c): граница — по z, p — по t (df ≥ 89). Это приближение консервативно: p по t не меньше p по z.
  - t1 и c1 промежуточного анализа считаются по n1 / n_max, где n1 — фактическое число задач этапа A после исключений, а n_max — плановое. На итоге c2 пересчитывается по фактической доле информации n1 / n.
  - α1 считается потраченной и тогда, когда промежуточный анализ «не определён».
  - **Бесполезность** (необязывающая, α её не учитывает): если на промежуточном среднее g ≤ 0, этап B не ставится.
  - Если на промежуточном выпало больше 20 % задач этапа A, промежуточный анализ ничего не останавливает (Т1 PRECOND-01). Выпавшими считаются задачи без пула; исключённые по EPS от рук не зависят и в знаменатель не входят. Пропавший голос — сбой с регретом 1, как в PRECOND-01.
  - Задача без пула исключается только явно, по закоммиченному списку `run/<этап>_exec_missing.json`. Пулы всех задач A и B коммитятся до правды A, и код это проверяет (`guard_pools`). Задача с пулом, но без правды — ошибка, а не пропуск.
  - Перед правдой этапа, перед заданиями B и перед промежуточным и итоговым анализом код сверяет sha256 файлов с `prereg_hashes.json` (`verify_hashes`).
  - Решение промежуточного анализа пишет код (`interim_an.json`). Задания этапа B код строит только при решении «продолжить», совпадающем с пересчётом (`guard_b_jobs`).
- **Исход:**
  - «REFUSE помогает» — граница пересечена на промежуточном или итоговом анализе;
  - «не показано» — иначе.

  Отрицательный исход REFUSE не опровергает: мощность при половине действия мала (§8).
- **Оценка при остановке на промежуточном** смещена вверх; в отчёте — пометка. Оценка этапа B отдельно — описательно.
- **Описательно, объявлено заранее:**
  - доля отказов по рукам;
  - вклад отказов (правило «отказ → A0»);
  - регрет ответивших голосов — условие после воздействия: руки им не сравниваются, вывода «без отказов лучше» нет;
  - выход на вызов по рукам — только по ответившим и отказавшимся голосам, без пропусков и сбоев (длина — посредник, причинно не проверяется);
  - число пропусков и сбоев по рукам;
  - регрет A0 без вызовов;
  - при исходе «не показано» — верхняя граница ДИ действия REFUSE. Решать по ней нельзя.
- **Чистота входа** (проверка, не вывод): у пяти голосов одной руки на одной задаче промпт один, поэтому вход первого запроса должен совпадать с точностью до естественного разброса (в пилоте 2–28 токенов). Флаг (`describe.input_span.flag`) ставится, если размах больше 100 токенов или доля пар «задача × рука» с размахом больше 30 выше 0,05. Снимок git добавлял около +400 (PRECOND-01) и +700…+1900 (SCORE-01). При флаге канал в отчёте считается не закрытым.
