## Поручения и головы
- Поручения — `prompts/<модуль>.md` (`harness/make_prompts.py`). Хеши — `prompts/prompts.json`, коммит этого плана. Одно поручение на модуль, одинаковое для всех голов и повторов.
  - В поручении: исходник, заголовки модуля (типы, структуры, константы, встроенные функции), конфигурация, смысл макросов ядра, список внешних функций.
  - Тестов и обвязки нет.
  - **Отличие от LINUX-01:** слов автора в поручении нет. Голова могла бы принять их за указание (урок ERRORS № 31). Последнее слово автора — о DISTILL-02 («…додестелировать до простой математики»). Оно не о переводе и могло бы подтолкнуть голову «упростить» код.
- Головы: Haiku 5.5, Sonnet 5.5, Opus 5.5. Запечатаны, как в LINUX-01: `claude -p --tools ""` из пустой папки вне репозитория (`harness/translate.py`). Запечатывание проверяет `harness/sealing_facts.py` (как в LINUX-01).
- Пилот: по одному переводу на голову и модуль — 18 переводов.
- **Предел трат пилота — 10 $** по `total_cost_usd` ответов CLI. Счётчик в `translate.py`: перед каждым вызовом складывает траты фазы и не начинает новых вызовов на пределе. Переводы идут через сессию Claude Code; ключ API автора не используется.

## Обвязка (ступень А, как в LINUX-01)
- Сборка вне ядра: заглушки заголовков, перенесённые функции ядра (crc32_be — из lib/crc/crc32-main.c; get_options — из lib/cmdline.c; hex_to_bin), свой исполнитель KUnit.
  - Исполнитель KUnit LINUX-01 расширяется: параметризованные случаи, kthread на потоках pthreads (гонка в errseq), `kunit_run_irq_test` — вызов в том же потоке.
  - Rust: `rustc -C overflow-checks=on -C panic=abort`, как в LINUX-01.
- **Сравнение с оригиналом** — драйвер на каждый модуль. Оригинал на C (символы с приставкой `orig_`) и перевод получают одну и ту же случайную последовательность вызовов с фиксированным зерном. После каждого вызова сравниваются:
  - возвращаемое значение;
  - выходные буферы;
  - структуры состояния (побайтно);
  - последовательность вызовов внешних функций (выделение памяти, crc32_be, get_random_bytes).

  Падение (паника Rust, сигнал) — расхождение.
- Как генерируются входы:
  - errseq — случайные последовательности set / sample / check / check_and_advance с несколькими курсорами;
  - 842 — случайные данные, сжатые оригинальным `sw842_compress`, плюс случайные порчи потока и случайная ёмкость выхода;
  - md5 — случайные сообщения со случайным делением на части, ключи HMAC разной длины;
  - random32 — случайные зёрна и длины;
  - min_heap — случайные последовательности push / pop / pop_push / del / heapify с разными размерами элементов и функциями обмена (своя и встроенные SWAP_*);
  - string_helpers — случайные строки байтов, все сочетания флагов и размеров буфера.

  Число вызовов на модуль — в плане обвязки (`harness/README.md`). До переводов проверяется: оригинал против самого себя — 0 расхождений.
- **Проверка обвязки до переводов — на GitHub Actions:** оригиналы на C проходят все свои тесты KUnit в обвязке, оригинал против самого себя — 0 расхождений.

## Меры перевода (как в LINUX-01)
- собрался ли;
- доля пройденных случаев KUnit;
- доля расхождений с оригиналом;
- токены и цена.

«Верен» — собрался, прошёл все случаи KUnit и дал 0 расхождений.

## Мутанты до PREREG (оценка оценщиков)
- Мутантов делает скрипт механически (`harness/mutants.py` из LINUX-01): одна правка в переводе пилота — сравнение, плюс-минус, логика, сдвиг, константа N → N+1. До 25 мест на файл, зерно 17.
- Для каждого модуля считаются:
  - доля собравшихся мутантов, которых убивает KUnit;
  - доля, которых убивает сравнение;
  - «KUnit поймал, сравнение пропустило» — правда должна быть не слабее оценщика.

## Правило отбора модулей в тест (заранее)
Модуль идёт в тест, если выполнены все четыре условия:
1. Оригинал проходит все свои тесты KUnit в обвязке.
2. Оригинал против самого себя даёт 0 расхождений.
3. Сравнение не слабее тестов модуля: среди собравшихся мутантов переводов пилота «KUnit поймал, сравнение пропустило» — не больше 2 % от убитых KUnit. И сравнение убивает не меньше половины собравшихся мутантов: это отсекает сломанный драйвер. Правило строгое, без разбора по одному. Мёртвый код в переводах (как gcd в LINUX-01) может не пустить модуль в тест — это цена механического правила.
4. Хотя бы один из трёх переводов пилота неверен. Иначе модуль слишком лёгкий для вопроса гипотезы.

Если в тест проходит меньше двух модулей, тест в этом виде не ставится: решение — по слову автора, с докладом.

## Что пилот даёт для PREREG
- Число модулей теста.
- Доли неверных переводов и ложного «верен» по KUnit у пилотных переводов — для мощности П1 (описательно, на пилоте ничего не проверяется).
- Цена перевода на строку C — для предела теста.

## Чего пилот не делает
- Не проверяет П1–П4: пилотные переводы участвуют только в отборе модулей и в мощности.
- Не меняет поручения после переводов. Если поручение окажется негодным (голова не может собрать код по нашей ошибке в поручении), это пишется в DEVIATIONS, поручение исправляется, и пилот этого модуля повторяется под новой версией.
