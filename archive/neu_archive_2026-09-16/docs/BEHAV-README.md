# BEHAV — базовый слой: поведение, симметрия, удержание

Программа: найти минимальную единицу «поведения» и правила усложнения,
пригодные от неживой материи вверх. Рабочее правило: **утверждение засчитывается,
только если оно что-то запрещает.** Конструкции без запретов — не результат.

Всё запускается: `./run_all.sh`. Результаты пишутся в `results/`.

## Журнал экспериментов

### BEHAV-040 / AR1 — ГРАНИЦА СПУСКА. Эксперимент невыполним, и причина системная

Ворота 2 дали отрицательный ответ ДО прогона. Количественный набор по
ревитализации существует (Global Survey, Pérez-Báez et al. 2019, 245
обследований, 40k единиц) — но он про ПРАКТИКИ, не про исходы. Поле само
признаёт пробел: программы не обязательно создают новых носителей, даже
самые обеспеченные не обязательно достигают результатов, а оценка
результатов — открытая проблема.

**Наблюдаемой «доля утраченного содержания, которая вернулась» на уровне
языка НЕ СУЩЕСТВУЕТ в счётном виде.** Эксперимент не ставится.
Записано как граница, а не как отрицательный результат.

**Что требуется, чтобы наша подпись была измерима — и где это есть:**
```
уровень        1) единицы     2) запись     3) запись     измеримо?
               опознаваемы    утраты        возврата
кодовая база       да            да            да            ДА
LTEE (геном)       да            да        возможна    нет: 2 события/6292
язык             частично       нет           нет            НЕТ
сома               да            да      смысла нет           НЕТ
```

**И отсюда следствие, которое ставит под вопрос весь метод спуска.**
Подпись «возврат содержания после утраты» измерима только там, где
система ВЕДЁТ ВНЕШНЮЮ ЗАПИСЬ собственной истории — git-лог, секвенирование.
Но внешняя запись И ЕСТЬ внешний эталон, то есть ровно то, что мы
пытались обнаружить (R2-ext против R3).

> **Мы систематически способны наблюдать возврат содержания только у
> систем с внешним эталоном. Значит методом «сломай и проверь
> содержание» нельзя показать отсутствие эталона — только его наличие.**

Это не оговорка, а структурное ограничение метода, и оно объясняет
задним числом две вещи: почему подпись подтвердилась на кодовой базе
(там эталон — сам git) и почему BEHAV-032 пришлось переклассифицировать
(там я мерил работу корректора, а не поломку).

**Статус спуска по уровням:** четыре уровня пройдены, форма инварианта
(скорость x ресурс^a = const) держится на всех четырёх, механизмы
различаются, а подпись удержания измерима ровно на одном. Дальше вниз
или вверх этим методом идти нельзя.

### BEHAV-039 / AR2 — «крупные возвращаются чаще» воспроизведено на втором проекте

```
страта                    pytorch    node (n)
мелкие                      0.53     0.062 (130)
средние                     0.61     0.058 (121)
крупные                     0.71     0.109 (128)
```
Направление совпадает: крупные изменения возвращаются примерно вдвое
чаще мелких в обоих проектах, при том что абсолютные уровни отличаются
на порядок (0.65 против 0.077).

**Это против расхожего практического поверья** («маленькие коммиты легче
вернуть»), и теперь оно держится на двух независимых проектах с разной
культурой. Формулировка слабая и точная:
> Вероятность возврата откатанного изменения РАСТЁТ с его размером.
> Воспроизведено на pytorch (n=711 выборка) и node (n=379, все откаты).
> На node возвратов всего 29, различие 0.062/0.109 при таком n не значимо
> по отдельности — вес даёт совпадение направления с pytorch, а не сам node.

ОГОВОРКА, записанная ДО прогона (ворота 3, п.5-7 списка): в меру размера
входят сгенерированные/вендорные файлы, whitespace и бампы сабмодулей;
отделить их без путей файлов нельзя. Эффект может частично отражать
не «размер работы», а тип файлов.

### BEHAV-038 / AP1(а) — ШЕСТОЕ и ПОСЛЕДНЕЕ объяснение отвергнуто. Поиск прекращён

Приоритет: «маленькие коммиты легче вернуть» — расхожая практическая
мудрость (блоги), исследований размера коммитов много, но связь
размер→возврат после отката не найдена.
Ворота 3 (запрет): список под «размером» выписан; п.5-7 (сгенерированные
файлы, whitespace, бампы сабмодулей) исключить нельзя без путей — оговорка
записана ДО прогона.
СТРОГИЙ КРИТЕРИЙ объявлен ДО прогона: после пяти отвергнутых кандидатов
засчитывается только МЕДИАЦИЯ (падение исчезает внутри страт), не
корреляция.

Технически: полная выгрузка diff нереальна (blob-ы лениво, ~1 коммит/сек,
30 часов на 109k). Взята стратифицированная выборка 711 откатов,
по 200 на бин глубины.

**Размер НЕ растёт с глубиной — гипотеза убита ещё до медиации:**
```
                     <1д     1-3д    3-10д     >10д
медиана строк        103      122      100       64
медиана файлов         3        4        4        2
```
Долгоживущие до отката коммиты в среднем МЕНЬШЕ, а не больше.

**Падение сохраняется во всех трёх стратах по размеру:**
```
страта                    <1д      1-3д     3-10д      >10д
мелкие (<49 стр)        0.685     0.481     0.508     0.347
средние                 0.706     0.632     0.600     0.465
крупные (>184 стр)      0.816     0.613     0.746     0.579
```
Медиации нет. **Условие смерти сработало.**

**Побочный результат, обратный поверью:** КРУПНЫЕ изменения возвращаются
ЧАЩЕ мелких во всех бинах глубины (0.816/0.613/0.746/0.579 против
0.685/0.481/0.508/0.347). Практическая мудрость «маленькое легче вернуть»
на этих данных не подтверждается — скорее наоборот, за крупное вложение
борются активнее. Приоритет не проверялся отдельно.

**ПОИСК ОБЪЯСНЕНИЯ ПРЕКРАЩЁН** по условию, объявленному в BEHAV-034.
Шесть отвергнутых кандидатов: причина отката, цензурирование, эпоха,
автор, тип отката, размер. Факт фиксируется как эмпирическая
закономерность БЕЗ МЕХАНИЗМА:

> В кодовой базе доля возврата откатанного содержания монотонно падает
> с временем, которое содержание прожило до отката (0.71 -> 0.44).
> Устойчиво к шести контролям. Механизм неизвестен.

Сцепление (кандидат «б») НЕ проверялось: требует путей файлов по всей
истории, что упирается в ту же выгрузку. Записано как непроверенный
кандидат, а не как отвергнутый.

### BEHAV-036 / AP2 — перенос персонализации: частично, и вскрыл главный конфаундер

```
проект    откатов  откат самим  возврат самим  возвр|активен  возвр|ушёл  разрыв
pytorch      5422        0.003          0.959          0.671       0.140    4.8x
node          381        0.344          0.704          0.077       0.023    3.4x
django         51        0.490          0.000          0.000       0.083    0.0x
```
- **Разрыв "активный автор / ушедший" ВОСПРОИЗВЁЛСЯ на node** (3.4x против
  4.8x у pytorch). На django n=51 и возврат нулевой — проверить нечего.
- **"Возврат делает сам автор" воспроизвелось**: 0.959 и 0.704.
  То есть закрытие оговорки BEHAV-031 (заголовок != содержание) держится
  на двух проектах.

**ГЛАВНОЕ: вскрыт конфаундер, который я не видел четыре хода.**
Доля откатов, сделанных САМИМ автором, различается радикально:
```
pytorch 0.003    node 0.344    django 0.490
```
У pytorch откат — это ВНЕШНЯЯ операция (бот, дежурный, mergebot),
у django — почти в половине случаев автор откатывает себя сам.
Это два РАЗНЫХ события под одним словом "revert":
  - внешний откат = вмешательство извне -> содержание может вернуться
  - самооткат = автор передумал -> возвращать нечего

И это же объясняет разброс уровней возврата между проектами
(0.655 / 0.075 / 0.020) лучше, чем культура Reland: где откат внешний,
там возврат высок; где самооткат — низок.
```
доля внешних откатов:  pytorch 0.997   node 0.656   django 0.510
доля возврата:         pytorch 0.655   node 0.075   django 0.020
```
Корреляция направления есть, но node/django ломают пропорцию —
значит объяснение частичное, не полное. Записано как гипотеза.

**Урок для протокола:** "revert" я взял как ОДНУ категорию, а под ней два
события с противоположным смыслом. Это ПЯТЫЙ случай корня "категория
шире, чем требует гипотеза" (#29,#33,#36,#40, теперь #50) — того самого,
под который я уже правил ворота 3. Правка не сработала: вопрос в воротах
есть, а я всё равно прошёл мимо. Значит вопроса мало, нужен ЗАПРЕТ:
не запускать, пока не выписан список событий, попадающих под ярлык.

### BEHAV-035 / AO1(в) — автор не объясняет падение, но объясняет УРОВЕНЬ

Приоритет: Yan et al. — "разработчик" самое дискриминирующее измерение при
предсказании ОТКАТА; предсказывает ли автор ВОЗВРАТ — не найдено.

**Разделение труда, найденное попутно и неожиданное:**
```
откаты делает автор оригинала:            0.3% (17 из 5422)
возвраты делает автор оригинала:         95.9%
```
Откатывает почти всегда кто-то другой (бот, дежурный), возвращает почти
всегда сам автор. **Это заодно закрывает оговорку #2 из BEHAV-031**
(совпадение заголовка не гарантирует совпадения содержания): если бы
совпадения были шумом, автор возврата не совпадал бы с автором оригинала
в 96% случаев.

**ДОСТУПНОСТЬ АВТОРА объясняет УРОВЕНЬ возврата — и очень сильно:**
```
ВОЗВРАТ при активном авторе (коммитит после отката):  0.671
ВОЗВРАТ при ушедшем авторе:                           0.140
```
Разница почти впятеро. Возврат содержания в кодовой базе — не свойство
эталона, а свойство ПРИСУТСТВИЯ КОНКРЕТНОГО ЧЕЛОВЕКА.

**Но падение с глубиной НЕ объясняет — условие смерти сработало:**
```
                          <1д         1-3д        3-10д         >10д
доля активных авт.      0.972        0.973        0.965        0.947
возврат|активен         0.721        0.629        0.600        0.444
возврат|ушёл            0.136        0.143        0.179            —
```
Доля активных авторов почти не меняется (0.972 -> 0.947), а падение
внутри группы активных полное (0.721 -> 0.444). У ушедших авторов
падения нет вовсе — возврат стабильно ~0.14.

**Четвёртое отвергнутое объяснение подряд.** Причина отката,
цензурирование, эпоха, автор — ни одно не объясняет падение.

**Что это меняет в рамке — существенно.** Мы искали механизм удержания
на уровне СИСТЕМЫ (эталон, тесты, ревью). Данные говорят, что на этом
уровне удержание содержания персонализировано: эталон определяет, ЧТО
должно быть, но возвращает содержание конкретный человек, и без него
возврат падает впятеро. Это ближе к нашему R3 (содержание в носителях),
чем к R2-ext, — и переклассификация BEHAV-031 в BEHAV-032 получает
второе, независимое подтверждение.

```
2024      0.777(605)   0.679(476)   0.616(211)            —
2025      0.734(793)   0.721(358)   0.651(215)    0.395(43)
2026      0.778(739)   0.588(330)   0.671(173)    0.553(38)
```
Падение с глубиной воспроизводится ВНУТРИ КАЖДОГО ГОДА — эпоха его не
объясняет. Но видно другое: **общий уровень возврата вырос с ~0.50 (2022)
до ~0.78 (2024-2026)**, то есть культура возврата в проекте усиливалась.
Это отдельное наблюдение, не объяснение падения.

**Итог трёх ходов.** Проверены и отвергнуты три объяснения падения
возврата с глубиной поломки: причина отката (BEHAV-033), цензурирование,
эпоха проекта. Эффект устойчив: 0.70 -> 0.42 при всех контролях,
воспроизводится внутри каждого года и при любом ограничении на окно.

**Это единственный уцелевший непонятый факт программы, и он теперь
защищён тремя контролями.** Формулировка слабая и точная:
> В кодовой базе доля возврата откатанного содержания монотонно падает
> с временем, которое содержание прожило до отката. Не объясняется
> причиной отката, цензурированием наблюдения или эпохой проекта.

### BEHAV-033 / AM1 — УСЛОВИЕ СМЕРТИ СРАБОТАЛО ВТОРОЙ РАЗ ПОДРЯД

Приоритет (ворота 2) дал прямое попадание ещё до прогона: Shimagaki et al.
(ICSME 2016) классифицировали откаты на внутренние/внешние и УЖЕ показали,
что откатанные по внешним причинам живут до отката ДОЛЬШЕ. То есть
корреляция "причина <-> глубина" опубликована, и наше падение возврата
с глубиной (BEHAV-032) могло целиком объясняться ею.

```
pytorch      n     доля  ВОЗВРАТ  мед.жизнь,д
транз.     790     0.15    0.646         0.72
сущест.     66     0.01    0.636         0.99
нет метки 4560     0.84    0.658         0.93

node         n     доля  ВОЗВРАТ  мед.жизнь,д
транз.     102     0.26    0.049         9.48
сущест.      6     0.02    0.167        24.92
нет метки  275     0.71    0.084        11.58
```
**Предрегистрация: "возврат высок у транзиентных и низок у существенных;
СМЕРТЬ: доли одинаковы у обоих типов -> объяснение неверно".**
У pytorch 0.646 против 0.636 — разница 1%. У node существенные дают
ВЫШЕ (0.167 против 0.049), то есть обратный знак при n=6.
**УСЛОВИЕ СМЕРТИ СРАБОТАЛО. Объяснение через причину отката неверно.**

**Падение с глубиной ВЫЖИВАЕТ внутри каждого класса:**
```
класс           <1д      1-3д     3-10д      >10д
транз.        0.667     0.631     0.602         —
нет метки     0.715     0.614     0.582     0.441
```
Значит глубина действует НЕЗАВИСИМО от причины. Механизм по-прежнему
не объяснён.

**Дополнительно: классификация по ключевым словам почти не работает.**
84% откатов у pytorch и 71% у node не содержат ни одного маркера.
Мой инструмент разметки слаб; вывод "причина не объясняет" опирается
на 16% размеченных и должен читаться с этой оговоркой.

**Итог двух ходов подряд:** сначала условие смерти убило перенос подписи
(BEHAV-032), теперь — объяснение того, почему он умер (BEHAV-033).
Падение возврата с глубиной поломки — устойчивый факт без объяснения.
Это единственное, что осталось, и оно записано как ОТКРЫТЫЙ ВОПРОС.

### BEHAV-032 / AL1+AL3 — УСЛОВИЕ СМЕРТИ СРАБОТАЛО. BEHAV-031 ПЕРЕКЛАССИФИЦИРОВАН

**AL1, репликация — провал по величине.**
```
проект    коммитов  revert    %  Reland  ВОЗВРАТ   нуль      x  строгий
pytorch     109322    5428  5.0     226    0.655  0.009   74.2    0.454
node         48006     385  0.8       4    0.075  0.006   12.6    0.068
django       34886      51  0.1       0    0.020  0.003    6.9    0.000
```
Направление уцелело (везде выше нуля), но абсолютная доля рухнула в 33 раза:
0.655 -> 0.020. У django строгий возврат РОВНО НОЛЬ (1 случай на 51 revert).
Эффект PyTorch в решающей мере — свойство КУЛЬТУРЫ проекта, а не уровня.

**AL3, зависимость от глубины — УСЛОВИЕ СМЕРТИ СРАБОТАЛО.**
```
дней жизни до отката      n   возврат
             <6ч       1187    0.688
           6ч-1д       1743    0.717
            1-3д       1575    0.617
           3-10д        803    0.585
          10-30д         97    0.433
            >30д         17    0.353
```
Предрегистрация гласила: "доля возврата НЕ падает с глубиной" (прогноз
из BEHAV-020, где у ext slam_50 на потолке), и "СМЕРТЬ: доля монотонно
падает -> кодовая база ведёт себя как template (R3), а не ext, и вывод
BEHAV-031 надо переклассифицировать".
Падение монотонное после первого бина: 0.717 -> 0.353, вдвое.
**По собственному правилу переигрывать нельзя. BEHAV-031 переклассифицирован.**

**Диагноз глубже, и он про АНАЛОГИЮ, а не про измерение.**
В симуляции поломка была ЭКЗОГЕННЫМ ШУМОМ: содержание портилось само,
эталон его восстанавливал. В кодовой базе revert — это НЕ поломка,
а РАБОТА самого механизма коррекции: эталон (тесты, ревью) выносит
суждение, что содержание было неверным. Тогда невозврат — это
ПРАВИЛЬНОЕ поведение ext, а не признак R3.
**Значит подпись "содержание возвращается после поломки" не различает
R2-ext и R3, если не знать, ЧЕГО ТРЕБУЕТ ЭТАЛОН.** Это существенное
ослабление, и оно бьёт по результату BEHAV-019/020, а не только по
его переносу.

**Что уцелело как наблюдение (не как результат).** Три проекта
выстраиваются в одну шкалу, и частота откатов идеально коррелирует
с долей возврата:
```
revert-rate  5.0%  ->  0.8%  ->  0.1%
возврат      0.655 -> 0.075 -> 0.020
```
Читается так: чем чаще проект ломается, тем чаще восстанавливает —
потому что частые поломки ТРАНЗИЕНТНЫ (сломал CI, вернул), а редкие
ПО СУЩЕСТВУ (изменение было неверным). Это гипотеза для BEHAV-033,
не вывод.

### BEHAV-031 / AK3 — [ПЕРЕКЛАССИФИЦИРОВАН в BEHAV-032] подпись R2-ext на реальных данных

Второй прогон по протоколу. Ворота пройдены, приоритет проверен
(тема занята: Yan EMSE 2019, 125k коммитов; ход "возвращается ли
откатанное" не найден), контроли и условие смерти записаны ДО.

Данные: PyTorch, 109 322 коммита, полная история.
Наблюдаемая УЗКАЯ (по новому вопросу ворот 3): вернулся ли ТОТ ЖЕ
заголовок или явный Reland — а не "файл снова тронули".

```
revert-ов: 5428 (5.0% — литература даёт 1-5%, сходится)
явных Reland-коммитов: 226

ВОЗВРАТ откатанного содержания        0.652
сопоставленный нуль                   0.011      -> 62x
СТРОГИЙ возврат (заголовок ровно 2х)  0.453
строгий сопоставленный нуль           0.001      -> 906x

задержка возврата: медиана 1.11 дня, квартили 0.30/4.57, доля <1 дня 0.48
```
**Прогноз (>0.20 и >=5x от базы) подтверждён с огромным запасом.
Условие смерти не сработало. Контрпрогноз против себя ("возврат редок,
потому что revert = идея была плохой") ОПРОВЕРГНУТ.**

**Ошибка в контроле, найденная и исправленная в том же ходе.** Первый
вырожденный контроль (перемешать заголовки) дал 0.411 — почти половину
сигнала. Разбор: перемешивание разрушает порядок времени, и сам исходный
коммит с вероятностью ~1/2 оказывается "после" отката. Нуль-модель была
неверна, не результат. Правильный СОПОСТАВЛЕННЫЙ нуль (случайная позиция
i + заголовок случайного коммита, существовавшего ДО i) даёт 0.011.

**Что это значит для программы.** Впервые подпись, выведенная в симуляции
(BEHAV-019/020: R2-ext ломается обратимо, содержание возвращается),
проверена на реальных данных ДРУГОГО уровня и подтвердилась
количественно. Два уровня ведут себя противоположно:
```
LTEE (BEHAV-030):     содержание почти не теряется (0.03% утрат)
                      -> ext НА ПОТОЛКЕ, ломать нечего
Кодовая база:         содержание теряется часто (5% откатов)
                      и ВОЗВРАЩАЕТСЯ в 65% случаев за ~1 день
                      -> ext В РАБОЧЕМ РЕЖИМЕ
```
Это две точки одной шкалы, а не два разных механизма: и там, и там
внешний эталон удерживает содержание. Различие в частоте поломок —
то самое окно наблюдаемости (BEHAV-025), теперь на реальных данных.

**Оговорки:** (1) один проект, конвенции PyTorch (явные Reland) могут
завышать; нужна проверка на репозитории с другой культурой; (2) совпадение
заголовков не гарантирует совпадения содержания — 70% совпавших заголовков
встречаются ровно дважды, что говорит против шаблонного мусора, но diff
не сверялся; (3) медиана возврата 1.11 дня, и 48% возвратов быстрее суток —
часть из них может быть "починил и вернул в рамках одной операции",
а не восстановлением после утраты.

### BEHAV-030 / AJ1 — эксперимент невозможен, и НЕВОЗМОЖНОСТЬ есть результат

Первый прогон по новому протоколу (gate.py пройден, приоритет проверен,
контроли и условие смерти записаны ДО).

Гипотеза: в LTEE среда = внешний эталон, значит утраченное закрепившееся
содержание возвращается в тот же ген.

**Данных для проверки НЕТ, и это содержательно:**
```
                    закреплений   событий F->E (утрата закреплённого)
немутаторы (6)             348                                     2
мутаторы   (6)            5944                                     0
```
Два события на 6292 закрепления = 0.03%. **Однажды закрепившееся
содержание в LTEE не теряется практически никогда.** Гипотеза AJ1
непроверяема: возвращаться нечему.

**Это ровно предсказание BEHAV-020 для ext:** там slam_50 упирался
в потолок 4096 — внешний эталон не даёт содержанию сломаться, пока он
доступен. LTEE при неизменной среде ведёт себя как ext на потолке.
Совпадение качественное; количественной проверки не получилось.

**ТРЕТЬЯ находка того же класса ошибок — сверка с BEHAV-028:**
```
поп   F->E    P->E   достигших F
p5       0      78            17
m6       1      92            60
p6       0    6616          1900
```
Инвариант «утрачивается ~0.6 закрепившегося» из BEHAV-028 считался по
переходам (F ИЛИ P) -> E и на 98%+ состоит из P->E — то есть из
полиморфизмов, которые НИКОГДА не закреплялись.
**ОТЗЫВ: это не удержание содержания, а отсев ПРЕДЛОЖЕНИЯ вариантов.**
Инвариант 0.6 остаётся фактом, но означает другое: доля обнаруженных
вариантов, не доходящих до закрепления.

Тот же корень, что в BEHAV-027 (поток событий вместо переворотов) и
BEHAV-029 (не та метрика): **я систематически беру более широкую
категорию, чем требует гипотеза.** Записано в POOL как повторяющийся
класс, а не как три отдельных случая.

**Следствие для программы:** LTEE не годится как тестовая площадка для
подписи "сломай и проверь содержание" — там нечего ломать. Нужна
система, где закреплённое содержание РЕАЛЬНО теряется. Кандидаты
записаны в PREREG (BEHAV-031).

Формат: предрегистрация → исход. Отозванные утверждения помечены **ОТОЗВАНО**.

### BEHAV-000 — батарея признаков габитуации (Tier-0)

Примитивы: B0 (интегральная ОС), B1 (расходуемый пул), гистероны (Прайзах).
Шесть одностимульных признаков H1–H6.

Предрегистрация: B0 проходит H1,H2,H4; гистероны без релаксации проваливают H2,H4.

Исход:
- Мостик **подтверждён**: между гистеронами с релаксацией и без переключаются
  ровно H2 и H4, остальные не двигаются. «Спонтанное восстановление ⇔ конечное τ;
  частотная чувствительность ⇔ рейт-зависимость».
- Оператор T (вторая шкала) переключает ровно H3 и H6.
- **ОТОЗВАНО**: «бактериальная адаптация формально того же класса, что габитуация».
  B0 проваливает 5 признаков из 6, и провал структурный: интегральная ОС
  адаптируется к среднему по времени, разреженные импульсы среднее не двигают.
  Потолок декремента ~30% при скважности 10%, скан τ_m по восьми порядкам.
  Адаптация и габитуация — **разные примитивы**.
- H5 (интенсивность) требует градуированного входа (механизм B0),
  H1/H2/H4 требуют расхода ресурса (механизм B1). Ни один примитив не даёт всё.

Приоритет: Smart, Shvartsman, Mönnigmann (arXiv:2608.00249) доказали
адаптация ⊥ габитуация раньше и строже (контрпримеры в обе стороны).
Наш аргумент про скважность — другой, даёт количественный потолок.

### BEHAV-001 — поведенческий слой (Виллемс)

Система = (𝕌, ℬ). Симметрия = замкнутость ℬ относительно g.
Ограничение = предикат на ℬ целиком. Потолок = «g ∈ G(ℬ) ⇒ C невыполнимо».

Предрегистрация: LTI-барьер воспроизводится; снятие симметрии открывает способность.

Исход:
- LTI-барьер воспроизведён, 0 нарушений потолка.
- **ГЛАВНОЕ, и оно ломает наивный тезис**: NL (аддитивность снята) всё равно
  проваливает H1. Значит нарушение симметрии **необходимо, но не достаточно**.
  Работает только контрапозиция: симметрия сохранена ⇒ ограничение невыполнимо.
  **Конструктивная половина программы отваливается.** Башню нельзя построить
  снятием симметрий; симметрии дают только пилу, отсекающую невозможное.
- Три бага в собственных детекторах найдены и починены: старт фильтра не из
  стационара; растяжение мерялось по сырым пикам (насыщение сигмоиды давало
  ложный проход); H2–H6 не были загейтены на H1.
- **ОТОЗВАНО**: H3 в булевом виде. Меняет знак от переформулировки метрики
  (внутрисерийное отношение vs первый отклик серии). Исключён из потолков.
- Число возможных историй: 3360 из 40320 (8.3%). **Плохо.** Причина: четыре
  предпосылки постулированы, не выведены. Цель: <100 (0.25%).

Выведенный метод: A ≺ B, если детектор B вырожден на всех системах без A.
Первая выведенная предпосылка: NL ≺ T2.

### BEHAV-001s — спектральное считывание

Ограничение = оператор, истинность = спектр. Последовательность пиков →
ганкелева матрица → ранг + собственные значения.

Исход:
- LTI: ранг 1, λ=0.535. Режим декремента **есть**; булев False был по порогу,
  а не по структуре. **Вчерашняя строка «потолок ok» прошла по порогу.**
- NL: вырожденная пара |λ|=0.505 — колебательный декремент. Булево «False»
  и спектральное «немонотонный декремент» — разные диагнозы.
- Pool+T2: две разделённые моды 0.882 / 0.569. **Инвариант τ₂/τ₁ = 1.55
  измерен прямо из поведения**, без доступа к модели.
- H3 объяснён: Pool(1) даёт ступеньку [0.791, 0.711, 0.711, 0.711],
  Pool+T2 — геометрию [0.783, 0.581, 0.512, 0.471]. Обе «убывают»;
  булев порог их не различает, спектр различает мгновенно.

Связка: угол между ограничениями. Пара (глубина декремента, восстановление),
сетка 6×6 по (k, τ_r): **cos θ = −0.834, θ = 146.5°**, И-шность 0.083.
Почти фрустрация. Булева таблица говорила «оба провалены» и выбрасывала
парето-фронт. Угол **измерен**, а не назначен выбором t-нормы.

### BEHAV-002 — протокол R: режим удержания

Сломать симметрию, убрать вход, мерить параметр порядка φ.

Исход:
- Гистероны без релаксации: φ = 0.607 неизменно через три порядка времени → **R1**.
- Гистероны с релаксацией: φ: 0.449 → 0.002 → **R2**, τ≈30.
- Пулы → R2, τ≈100. **Долг:** необъяснённый остаток φ ≈ 0.10–0.28 вместо нуля.
- Ось ортогональна признакам габитуации: по H1/H2/H4 гистероны с релаксацией
  и без стояли рядом, по удержанию — в разных классах.

R3 (удержание копированием), N носителей, порча ε, коррекция по большинству μ:
```
    μ       N=5   N=11   N=21   N=41
  0.00       33     34     31     30      ← избыточность не помогает
  0.10      108    280  15883  20000      ← скачок на два порядка
```
**R3 — не «R2 с большим τ», а другая фаза с порогом.** Обостряется с N.
Это порог ошибок Эйгена (1971) в игрушечном виде; новое — использование
его как классификатора уровня по оси удержания.

### BEHAV-003 — связывание осей

Инвариант T2 (отвечает за H6) несётся слоем носителей.

Предрегистрация: P1 repair гладко; P2 template с порогом; P3 потеря селективна;
P4 ранг падает 2→1; P5 поведенческий порог ≥ битового.

Исход:
- **P1 ✓**: repair даёт φ* = μ/(μ+ε), совпадает до третьего знака, N не влияет.
- **P2 ✓**: template даёт порог, движущийся с N (N=11: между 0.10 и 0.15;
  N=41: между 0.02 и 0.04).
- **P3 ✓ — главное**: H1 выживает при полном разрушении слоя, H6 умирает.
  **Потеря селективна и идёт сверху вниз по башне.**
- **P5 ✓**: биты живут при φ=0.098, H6 уже мёртв. Поведению нужна рабочая доля
  ≈0.2. **Система теряет функцию раньше, чем теряет информацию.**
- **P4 ✗ уточнено**: ранг зависит от **окна протокола**.
  ```
  k_deep/k0   ранг(20 имп)   ранг(120 имп)
       0.25        1              3
  ```
  **ОТОЗВАНО**: «ранг = число инвариантов системы».
  Верно: **ранг = число инвариантов, активных в данном окне наблюдения.**
  Любое утверждение об инвариантах обязано указывать протокол.

### BEHAV-004 — конструктивное направление и самодостаточность

Инвариант: **вырожденный выбор**. Бит без внешнего эталона (гомохиральность).
Шум симметричный: носитель принимает случайный бит, а не портится в сторону.

Предрегистрация: P6 none не держит, плоско по N; P7 ext схлопывается при
отключении эталона; P8 template не замечает; P9 время удержания разделяет
R2 и R3 по N; P10 порог движется с N.

Исход:
- **P6 ✓**: none держит 78/67/88/76 шагов при N = 11/41/161/641.
  Рост избыточности в 58 раз не даёт ничего.
- **P9 ✗ — самый ценный провал.** Времена удержания ext и template
  **совпадают в точности** (296/4000/4000/4000 у обоих при μ=0.05).
  N-зависимость **не** разделяет R2 и R3, если у R2 есть внешний эталон.
- **P7 ✓, P8 ✓ — настоящий разделитель.** Отключение эталона на шаге 400:
  ```
  шаг:          0    200    399  |  450    600    900   1300
  ext        0.975  0.938  0.913 | 0.292  0.019 -0.006 -0.043   ← симметрия восстановлена
  template   0.975  0.938  0.913 | 0.950  0.913  0.938  0.975   ← не заметил
  ```
- **P10 ✓**: порог по μ движется вниз с ростом N.

**Вывод, переписывающий ось:** R2 и R3 неразличимы, пока внешний эталон
присутствует. Они различаются **только** при его удалении.

## Достигнутые утверждения

**Запрещающие:**
1. Симметрия ℬ ⇒ соответствующее ограничение невыполнимо (LTI-барьер, воспроизведён).
2. Интегральная ОС не даёт глубокой габитуации к разреженным импульсам;
   потолок задан скважностью.
3. Глубина декремента и скорость восстановления в одноинтеграторной системе
   не могут быть резкими одновременно (θ=146.5°, парето-фронт).
4. R2 без внешнего эталона не удерживает вырожденный выбор **ни при каком N**.
5. Функция теряется раньше информации (порог 0.2 против 0.098).

**Конструктивные (единственное на всю программу):**
6. R3 удерживает вырожденный выбор без внешнего эталона выше μ_c(N),
   и μ_c падает с ростом N.

**Критерий самодостаточности (закрывает дыру R2.5):**
> Система самодостаточна по инварианту I, если время удержания I
> не меняется при отключении всех внешних источников информации об I.

Проверяется протоколом отключения. Для ячейки Бенара невыполним:
варьировать нечего — что, возможно, и есть ответ.

## Открытые долги

1. **R0 образца нет.** Ось неполна.
2. **Остаток φ ≈ 0.1 у пулов (BEHAV-002) не объяснён.**
3. **Матрица углов померена для одной пары.** Нужна полная.
4. **Число историй 3360.** Постулированные предпосылки надо заменить выведенными
   через процедуру инертности. Цель <100.
5. **Распознавание R3-слоя в системе с неизвестным устройством.**
   Протокол отключения требует доступа к «внешнему эталону», который надо
   сначала опознать.
6. **Эмпирических данных нет вообще.** Всё — самосогласованная симуляция.
   Главная слабость программы.
7. **Обратное направление для остальных инвариантов не проверено.**
   Показано только для T2/H6.
